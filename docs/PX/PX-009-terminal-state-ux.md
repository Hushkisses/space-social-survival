## Goal

Terminal player states must be immediately understandable. A player who dies, becomes an infected post-death form, is detained, access-restricted or ejected should know:

- what happened,
- what state they are now in,
- what they can still do,
- what they can no longer do.

Existing core death/sanction state remains authoritative.

## Death

On death:

- normal Minecraft inventory dropping remains enabled,
- functional equipment and physical resources remain recoverable,
- telemetry continues to record recoverable drop stacks/units,
- death location is preserved for the post-death transition.

Normal dead state:

- respawns at the death location,
- switches to Spectator,
- receives a clear death title,
- is told that living players cannot hear their normal chat,
- is told that private objectives remain secret until match end,
- is reminded that dropped equipment/resources remain recoverable.

## Living / Dead communication

Normal text chat is separated:

- living -> living only,
- dead/infected-post-death -> dead/infected-post-death only.

This follows the existing core communication rule that living and dead players cannot directly communicate.

## Infected post-death form

When the active infection scenario converts an infected dead player:

- respawns in Adventure mode rather than Spectator,
- receives a strong infected-conversion presentation,
- is explicitly told that normal living communication, facility repair and hull repair are unavailable,
- receives the post-death goals already generated by `InfectedPlayerService`:
  - infect others,
  - breach restricted zones,
  - attack facilities.

No hidden infection identity is revealed before the existing death/conversion event makes the new form relevant.

## Detention

Habitation now contains a physical detention cell.

Physical layout:

- 5x5 barred outer cell,
- 3x3 walkable interior,
- visible red floor marker,
- fixed detention spawn point.

When detention executes:

- target is moved into the cell,
- title/sound presentation explains detention,
- the player can walk inside the cell,
- attempts to leave are blocked,
- repeated escape warnings use compact ActionBar feedback,
- facility work is blocked while detained,
- PDA/inventory remain available.

No arbitrary detention duration was invented. UI says the restriction remains while the sanction state remains active.

## Access restriction

On successful access restriction:

- strong title/sound feedback is shown,
- facility-console restriction is stated,
- existing physical doorway restriction remains authoritative,
- unrestricted public movement and PDA use are explicitly distinguished from blocked actions.

## Ejection

Ejection still requires the existing sanction execution prerequisite: an available generated airlock.

Successful ejection is staged:

1. move target to the generated airlock,
2. show depressurization/ejection presentation,
3. after a short transition, switch to Spectator,
4. move view outside the airlock side of the ship,
5. explain that living-crew actions are over and private objectives remain hidden.

If the map has no airlock, the existing `SanctionExecutor` prerequisite prevents ejection from executing.

## Facility / repair enforcement

Dead and infected-post-death players cannot:

- operate facility consoles,
- repair physical hull breaches.

Detained players cannot operate facility consoles.

Existing access-restriction and ejection enforcement remains in place.

## Validation checklist

### Death
1. die while carrying a functional item and physical resource,
2. confirm drops remain on the ground,
3. respawn,
4. confirm normal death becomes Spectator,
5. confirm title/messages are understandable,
6. confirm dead chat is not visible to living player,
7. confirm dead-to-dead chat remains visible.

### Infection conversion
1. activate infection scenario,
2. make an infected participant die,
3. confirm Adventure infected form,
4. confirm new-goal explanation,
5. confirm facility console and hull repair denial.

### Detention
1. execute a successful detention vote,
2. confirm target moves into Habitation detention cell,
3. walk inside the cell,
4. confirm movement inside is allowed,
5. attempt to cross the bars/bounds,
6. confirm escape is blocked,
7. confirm facility work is unavailable.

### Access restriction
1. execute access restriction,
2. confirm title/message,
3. confirm facility console denial,
4. confirm restricted doorway denial.

### Ejection
1. use a seed that generated `airlock_1`,
2. execute ejection,
3. confirm airlock transition,
4. confirm delayed Spectator conversion,
5. confirm outside-ship viewpoint,
6. confirm facility/ship interaction is no longer possible.


## Solo validation commands

Start a one-player development match first.

For general PX-009 validation:

```text
/space match devstart
```

or use a fixed seed.

### Death

```text
/space match devstate death
```

### Detention

```text
/space match devstate detain
```

The player should be moved into the Habitation detention cell, be able to walk inside its 3x3 interior, and be unable to leave.

### Access restriction

```text
/space match devstate access
```

Facility consoles and restricted physical thresholds should reject interaction with Korean feedback.

### Ejection

Use the stable validation seed:

```text
/space match devstart 1000
```

Seed 1000 is protected by an automated test to include `airlock_1`.

Then run:

```text
/space match devstate eject
```

The player should move to the airlock, see the depressurization transition, then become Spectator outside the ship after the short delay.

### Reset

```text
/space match reset
```

Use reset between sanction-state tests because current sanction state is match-runtime state.
